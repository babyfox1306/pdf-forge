Working with a PDF collection

Practical notes for converting a folder of PDFs into a Markdown corpus your editor and coding agent can actually work with.

You reached this page because a batch run crossed the monthly threshold. Nothing is broken — the files already converted are complete and usable. Below is how to work through a collection efficiently.

Convert by subtree, not all at once

Running the command on a workspace root scans everything beneath it. Running it on a subfolder scans only that subtree, and the index merges across runs rather than replacing itself:

docs/api/        → run 1
docs/guides/     → run 2
manuals/         → run 3

After all three runs, pdf-forge-exports/INDEX.md lists every document from every run. Removing a source under docs/api/ and rescanning that subtree only affects entries under docs/api/; entries from manuals/ stay untouched.

Convert the subtree you actually reference first. Reference material an agent never reads costs you the same as material it reads daily.

Re-running is cheap

A file whose source has not changed is recorded as unchanged. It is not reconverted and does not count toward the monthly threshold. Only a new or modified source counts, and only once per revision.

This means you can safely re-run the command on the same folder after adding a few PDFs. Only the new ones do work.

Read INDEX.md before trusting the corpus

Every row carries a status. The ones worth checking:

StatusWhat it means
convertedFull text extracted, Markdown written.
low_textSome text extracted, but far less than the page count suggests. Usually a mostly-image document. The Markdown carries a warning at the top.
no_textNo usable text layer. No Markdown written. These need OCR elsewhere first.
encryptedPassword-protected. Decrypt before converting.
skipped_limitNot converted this month because the batch threshold was reached. Retryable.
conflictYou edited the generated Markdown by hand. Nothing was overwritten.

A corpus with several no_text rows will silently mislead an agent — it will confidently answer from the documents it can see and never mention the ones it cannot. Check the index before pointing an agent at the folder.

Point the agent at the index, not the folder

Coding agents handle a single named entry point far better than a directory tree they have to explore. Referencing pdf-forge-exports/INDEX.md gives the agent the document list, page counts, and relative links in one read, and every generated file carries front matter identifying its source PDF:

---
title: "Authentication: API Reference"
source: "docs/api/authentication.pdf"
pages: 42
status: "converted"
---

That source field is what lets an answer be traced back to a specific PDF rather than to an anonymous block of text.

Commit the corpus

Markdown diffs; PDFs do not. Committing pdf-forge-exports/ means a change to a spec shows up as a readable diff in review instead of an opaque binary blob.

Keep .pdf-forge-manifest.json alongside it. That file records which outputs were generated by the tool and which revision they came from. Without it, a clone on another machine cannot prove ownership of the existing output and will refuse to overwrite anything — which is the safe behaviour, but an inconvenient one.
