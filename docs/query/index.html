Querying the document collection

Getting a coding agent to use a converted corpus well, rather than wandering through it.

Give it the index, not the directory

A directory of Markdown files is a poor interface for an agent. It has to list, guess from filenames, open several, and discard most of what it reads. On a corpus of any size that burns context before the real question is answered.

pdf-forge-exports/INDEX.md is the entry point. One read gives the agent every document's title, source path, page count, status, and a relative link. It can then open exactly what it needs.

In practice, referencing the index explicitly works better than hoping the agent finds it:

Read pdf-forge-exports/INDEX.md first to see which documents
exist, then open only the ones relevant to the question.

Plain search still does most of the work

Because the corpus is ordinary Markdown inside the repository, everything already built for code applies to it. Editor-wide search finds a term across every converted document. git grep works. git log -p on a converted file shows how a specification changed over time — something that is effectively impossible with the PDFs themselves.

This is the part that is easy to overlook: the corpus does not need a special retrieval system to be queryable. It needs to be text, in the repo, with stable paths.

Provenance is what makes an answer checkable

Every generated file opens with front matter naming its source:

---
title: "Authentication: API Reference"
source: "docs/api/authentication.pdf"
pages: 42
status: "converted"
---

That field is the difference between "the docs say X" and "docs/api/authentication.pdf says X". The second can be verified by opening the original; the first cannot. If you ask an agent to cite the source value alongside its answers, every claim becomes traceable back to a specific PDF.

Tell the agent what is missing

The failure mode worth guarding against: a document that did not convert is invisible, and invisible reads as "not relevant" rather than "not available". An agent will answer around the gap without ever flagging it.

The index carries statuses for exactly this reason — no_text, encrypted, skipped_limit. Since the agent reads the index anyway, it can be told to treat those rows as known gaps and say so when a question falls near one.

Feeding a retrieval pipeline

If the corpus is being chunked into a vector store rather than read directly, the front matter is the metadata layer: carry source and pages onto each chunk so retrieved passages stay attributable. A retrieval system that returns text without a document identity produces answers nobody can check.

Reconvert before reindexing. A stale index over a fresh corpus is the same silent-drift problem, one layer further from where you would notice it.

PDF Forge does not upload documents or document text. This is a public GitHub Pages page; it receives no document data of any kind.
